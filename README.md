## ข้อมูลโครงการฉบับเต็ม (schema 4)

ฟอร์มเพิ่ม/แก้ไขโครงการแบ่งเป็น 4 แท็บและบันทึกพร้อมกัน ไม่มีส่วน “ปริมาณงาน”:

- **ข้อมูลโครงการ:** ชื่อเต็ม ชื่อย่อ รหัสอัตโนมัติ ผู้อำนวยการ หน่วยงาน สายงาน วัตถุประสงค์ พื้นที่ วันเริ่ม–สิ้นสุด
- **วงเงินลงทุน:** เงินกู้ เงินรายได้ OH/IDC ภายในเงินรายได้ และยอดเบิกจ่ายสะสมแยกตามแหล่งเงิน รวมวงเงินคำนวณจากเงินกู้ + เงินรายได้เท่านั้น
- **สถานะ:** โครงการใหม่/ต่อเนื่อง วันที่มติ ครม. สถานะล่าสุด ความคืบหน้า และหมายเหตุ
- **ผลตอบแทน:** Payback Period, NPV, FIRR, EIRR วันที่และที่มาผลศึกษา ค่าที่ยังไม่ทราบเก็บเป็น null ไม่แทนด้วย 0; NPV และอัตราผลตอบแทนติดลบได้ตามผลศึกษา

หนึ่งโครงการใช้ทั้งเงินกู้และเงินรายได้ได้พร้อมกัน `OH + IDC ≤ เงินรายได้` และเบิกจ่ายของแต่ละแหล่งต้องไม่เกินวงเงินของแหล่งนั้น กราฟสรุปแยกยอดตามวงเงินจริง ไม่จัดยอดทั้งโครงการให้แหล่งเดียว CSV/JSON รวมข้อมูลใหม่ และโครงการที่นำเข้ารอบประชุมใหม่จะเก็บรายละเอียดเต็มเป็น snapshot

การย้ายข้อมูลเดิมเก็บยอดรวมและยอดเบิกจ่ายไว้ครบ โครงการเงินกู้/เงินรายได้เดิมถูกจัดเข้าวงเงินที่ตรงกัน ส่วน OH/IDC เดิมถือเป็นส่วนของเงินรายได้ หากแหล่งเงินเดิมไม่ชัดเจนจะคงไว้ในยอดรอจัดแหล่งเงิน พร้อมแจ้งให้ผู้ใช้จัดประเภทก่อนบันทึกฟอร์มใหม่ ไม่มีการเดาหรือแบ่งสัดส่วนยอดเงิน ข้อมูลรอบประชุมเก่าคง snapshot เดิมไว้

## ประชุมงบประมาณ

เมนู **ประชุมงบประมาณ** อยู่ระหว่างประมาณการและรายงาน ใช้ Sidebar/Header เดิมและเปลี่ยนเฉพาะพื้นที่กลาง เปิดตรงได้ที่ `http://127.0.0.1:8080/#meetings`

1. สร้างรอบประชุม โดยระบุปี พ.ศ. ครั้งที่ ชื่อ และวันที่ ปี/ครั้งที่ต้องไม่ซ้ำกัน
2. เลือกโครงการจาก Master DB ระบบบันทึกภาพข้อมูล ณ ตอนนำเข้ารอบเป็นงบก่อนประชุม ข้อมูลนี้ไม่เปลี่ยนเมื่อโครงการหลักเปลี่ยน
3. คลิกโครงการเพื่อเปิด 4 แท็บ: ข้อมูลโครงการ, แผนงบประมาณ, รายละเอียดเปลี่ยนแปลงงบ, มติและบันทึก
4. แผนรายเดือนใช้มกราคม–ธันวาคมของปีประชุม หน่วยล้านบาท ผลรวมไม่เกินงบหลังประชุม เมื่อเปลี่ยนงบต้องระบุเหตุผล
5. บันทึกผลและเลือก “พิจารณาโครงการนี้แล้ว” ระบบสรุปยอดก่อน/หลัง ผลต่าง และจำนวนที่รอพิจารณา รายการที่ยังไม่ได้แก้ไขใช้ยอดก่อนประชุมเป็นค่าเริ่มต้น
6. ปิดรอบได้เมื่อพิจารณาครบทุกโครงการ หลังปิดอ่านข้อมูลและประวัติได้ แต่แก้ไขไม่ได้

ผลประชุมเป็นข้อมูลแยกจากงบในโครงการหลัก ไม่เขียนทับ Master DB อัตโนมัติ แผนรายเดือนเป็นแผนของรอบประชุม ไม่ใช่รายการเบิกจ่ายจริง ข้อมูลอยู่ในตาราง `budget_meetings`, `meeting_projects`, `meeting_project_events` (schema 3) การสำรอง SQLite รวมโมดูลประชุมทั้งหมด ส่วน JSON export เดิมส่งออกเฉพาะโครงการหลักและข้อมูลหลัก

ทดสอบโมดูลด้วย `python -m unittest -v test_meetings.py`, `python verify_meetings.py` และ `python verify_meetings.py --mobile` โดยใช้ฐานข้อมูลทดสอบแยกจากข้อมูลจริง

เว็บแอปจัดการงบประมาณโครงการ ภาษาไทย พร้อมรหัสโครงการอัตโนมัติ ฐานข้อมูล SQLite และ REST API สำหรับต่อยอด

## เริ่มใช้งาน

ใช้ Python 3.11 ขึ้นไป เปิด Terminal ในโฟลเดอร์โปรเจกต์ แล้วรัน:

```powershell
python -m pip install -r requirements.txt
python server.py
```

เปิด http://127.0.0.1:8080 หรือใช้ `./start.ps1` หลังติดตั้ง dependency แล้ว ต้องเปิดผ่านเซิร์ฟเวอร์นี้ ไม่ใช่เปิด `index.html` โดยตรงหรือใช้ Live Server เพราะหน้าเว็บเรียก API ที่ origin เดียวกัน

ฐานข้อมูลจะสร้างที่ `data/master.db` เมื่อเริ่มเซิร์ฟเวอร์ มีแหล่งเงินและสถานะเริ่มต้น แต่ไม่มีโครงการตัวอย่างปนกับข้อมูลจริง การปิดเบราว์เซอร์หรือรีสตาร์ตเซิร์ฟเวอร์ไม่ทำให้ข้อมูลหาย ตั้ง `P_BUDGET_DB` เพื่อเปลี่ยนตำแหน่งฐานข้อมูล และ `PORT` เพื่อเปลี่ยนพอร์ตได้

## รหัสโครงการอัตโนมัติ

- รูปแบบ `PRJ-2569-00001` ใช้ปีปฏิทิน พ.ศ. ตามวันที่สร้างในเวลาไทย ไม่ใช่ปีงบประมาณ
- ออกเลขเมื่อบันทึกสำเร็จเท่านั้น การเปิดฟอร์มหรือยกเลิกไม่ใช้เลข
- แต่ละปีเริ่มที่ `00001`; ถ้าเกินห้าหลักจะเพิ่มจำนวนหลักได้
- จัดสรรเลขและบันทึกโครงการใน transaction เดียวด้วย `BEGIN IMMEDIATE` พร้อม unique constraint เพื่อป้องกันเลขซ้ำเมื่อบันทึกพร้อมกัน
- รหัสและ ID แก้ไขไม่ได้ โครงการใหม่มี UUID ถาวรสำหรับเชื่อมกับตารางในอนาคต
- การลบเป็น soft delete เก็บประวัติและไม่ใช้รหัสเดิมซ้ำ
- ข้อมูลนำเข้าคงรหัสเดิม ถ้ารหัสตรงรูปแบบ `PRJ-ปี-เลข` ระบบจะปรับตัวนับขึ้นเพื่อไม่ออกเลขชนกัน

## ข้อมูลหลักและการแก้ไข

มีเงินกู้และเงินรายได้เป็นแหล่งเงินหลักเท่านั้น OH/IDC เป็นส่วนประกอบภายในเงินรายได้ ฟอร์มปัจจุบันกรอกวงเงินได้ทั้งสองแหล่งพร้อมกัน ตามกติกา schema 4 ด้านบน

แหล่งเงินหลักและส่วนประกอบกำหนดไว้ตามโครงสร้างนี้ ไม่สามารถเพิ่มแหล่งเงินที่สามได้ ส่วนสถานะยังเพิ่มได้ตามปกติ

เมนู **ข้อมูลหลัก** จัดการสถานะ และเปิด/ปิดใช้งานแหล่งเงินที่กำหนดไว้ได้ ไม่เพิ่มแหล่งเงินหลักอื่น รหัสข้อมูลหลักคงเดิม

รายการที่ปิดใช้งานจะไม่ปรากฏในตัวเลือกโครงการใหม่ แต่โครงการเดิมยังใช้อ้างอิงได้ สถานะสามารถระบุว่าเป็นสถานะสิ้นสุดโครงการเพื่อใช้คำนวณจำนวนโครงการที่ยังดำเนินการ

การแก้ไขและลบส่ง `version` ปัจจุบัน หากมีการแก้ไขจากหน้าต่างอื่นก่อน ระบบตอบ `409` เพื่อป้องกันการเขียนทับ ให้ปิดฟอร์มแล้วเปิดใหม่หลังโหลดข้อมูลล่าสุด

## นำเข้าข้อมูลเดิม

หน้า **ตั้งค่า** รองรับ JSON แบบ array จากเวอร์ชันเดิม และ JSON export ของเวอร์ชันนี้ นำเข้าเพิ่มเท่านั้น ไม่ล้างฐานข้อมูล:

1. ถ้าใช้งานที่ URL และเบราว์เซอร์เดิม เลือก **นำเข้าข้อมูลจากเบราว์เซอร์เดิม**
2. ถ้าเดิมเปิดไฟล์โดยตรง ให้เปิด `index.html` ด้วยเบราว์เซอร์/ตำแหน่งไฟล์เดิม เข้า **ตั้งค่า → ส่งออกข้อมูลเบราว์เซอร์เดิม** (ใช้ได้แม้ยังไม่เชื่อม API) แล้วเปิด http://127.0.0.1:8080 เพื่อนำเข้า JSON
3. ข้อมูลเดิมใน localStorage จะไม่ถูกลบ

รหัสและ ID เดิมจะถูกเก็บไว้ถ้าไม่ซ้ำ ข้อมูลที่รหัสเดียวกันและรายละเอียดตรงกันจะข้าม หากข้อมูลต่างกัน หรือชนรหัสของรายการที่ลบแล้ว ระบบยกเลิกทั้งชุดโดยไม่มีการนำเข้าบางส่วน ชื่อแหล่งเงินและสถานะของ JSON เก่าต้องมีในข้อมูลหลักก่อน

## สำรองและกู้คืน

หน้า **ตั้งค่า → ดาวน์โหลดฐานข้อมูล SQLite** สร้าง snapshot ที่สอดคล้องกันด้วย SQLite backup API รวมโครงการ ข้อมูลหลัก ประวัติ รายการที่ลบ เลขรัน และ schema version

กู้คืนโดยหยุดเซิร์ฟเวอร์ เก็บสำรองโฟลเดอร์ `data` เดิมไว้ แล้วนำไฟล์ที่ดาวน์โหลดมาใช้เป็น `master.db` ในโฟลเดอร์ใหม่ ตั้ง `P_BUDGET_DB` ไปยังไฟล์นั้น และเริ่มเซิร์ฟเวอร์ใหม่ ห้ามนำไฟล์ WAL/SHM จากฐานข้อมูลเก่ามาปะปนกับ snapshot

**ส่งออกโครงการ JSON** เหมาะกับการย้ายรายการที่ยังใช้งานและข้อมูลหลัก ไม่ใช่ backup เต็ม: ไม่รวมประวัติ รายการที่ลบ หรือเลขรันที่เคยใช้แล้ว การนำเข้าจะสร้างเวลาและประวัติการนำเข้าใหม่ ถ้าต้องการรักษาข้อมูลทั้งหมดให้ใช้ SQLite snapshot

## โครงสร้างสำหรับต่อยอด

โค้ด Dashboard, กราฟ, ตารางแผนและผล, ไอคอน และหัวเมนูแยกไว้ใน `frontend/` ดูหน้าที่แต่ละไฟล์และลำดับการโหลดได้ที่ [frontend/README.md](frontend/README.md) ส่วน `app.js` เป็นจุดประกอบโมดูลและประสานงานกับข้อมูลแอป

| ตาราง | หน้าที่ |
|---|---|
| `projects` | ข้อมูลหลักโครงการ, UUID, รหัส, จำนวนเงิน, ความคืบหน้า, version, timestamps, soft delete |
| `funding_sources` | ข้อมูลหลักแหล่งเงิน |
| `project_statuses` | ข้อมูลหลักสถานะและตัวบอกสิ้นสุดโครงการ |
| `project_sequences` | เลขรันสูงสุดแยกตามปี พ.ศ. |
| `project_events` | snapshot ของการสร้าง แก้ไข ลบ และนำเข้าโครงการ |
| `schema_migrations` | เวอร์ชันโครงสร้างฐานข้อมูล |

จำนวนเงินในฐานข้อมูลเก็บเป็นจำนวนเต็มหน่วยบาท (`budget_baht`, `spent_baht`) เพื่อหลีกเลี่ยงการเก็บเงินเป็น floating point หน้าจอและ API ใช้ล้านบาท ทศนิยมสูงสุด 3 ตำแหน่ง; ความละเอียดขั้นต่ำ 1,000 บาท

โมดูลในอนาคต เช่น แผนเบิกจ่ายรายเดือน สัญญา และรายการเบิกจ่าย ควรเชื่อมด้วย `project_id REFERENCES projects(id)` ไม่ใช้ชื่อหรือรหัสโครงการเป็น foreign key

ไฟล์หลัก: `server.py` (API และกติกาข้อมูล), `migrations/001_master.sql` (schema), `app.js` (หน้าจอ), `index.html`, `style.css` รายละเอียด API อยู่ใน [API.md](API.md)

สร้างรอบประชุม เลือกโครงการจาก Master DB หรือใช้ปุ่มนำเข้าไฟล์ประชุมเดิม `.mbg` / `.db` ที่ท้ายหน้า การนำเข้าเพิ่มเป็นรอบใหม่และไม่แทนที่ข้อมูลเดิม โครงการร่างที่ยังไม่มีวงเงินเก็บยอดศูนย์ได้ รหัสโครงการสร้างอัตโนมัติและเก็บรหัสเดิมในข้อมูลการนำเข้า

อ่านรายละเอียดสูตร การเก็บข้อมูล และข้อแตกต่างจากการเปิดไฟล์แบบเดิมใน [meeting-app/INTEGRATION.md](meeting-app/INTEGRATION.md) สำรอง SQLite จากเมนูตั้งค่าเพื่อเก็บข้อมูลครบทั้ง Master DB และการประชุม

## หน้า 9 ช่อง: SQLite และออฟไลน์ (ฐานข้อมูลรุ่น 6)

เมื่อฐานข้อมูลยังไม่มีข้อมูล 9 ช่องและไม่มีข้อมูลเก่าในเบราว์เซอร์ หน้าจอจะแสดง “เลือกปีงบประมาณเริ่มต้น” ค่าแนะนำคือปีปฏิทิน พ.ศ. ปัจจุบันตามเวลาไทย ผู้ใช้เลือกปีงบประมาณเองได้ระหว่าง 2500–2700 แล้วกด “เริ่มใช้งานปีนี้” ระบบบันทึกปีที่เลือกลง SQLite ก่อนเปิดให้แก้ตาราง ไม่ได้เริ่มที่ 2566 ตายตัว และไม่เปลี่ยนปีที่บันทึกไว้เมื่อขึ้นปีใหม่

ข้อมูล SQLite หรือ localStorage เดิมยังใช้ปีเดิมโดยไม่แสดงหน้าตั้งค่าซ้ำ สามารถนำเข้า JSON เดิมได้จากหน้าตั้งค่าปีโดยตรง ปีในไฟล์จะถูกเก็บไว้ การเพิ่มปีถัดไปยังใช้ปีสูงสุดที่มีอยู่และไม่เกิน 2700

ชุด EXE ล่าสุดที่รวมข้อ 1–7 อยู่ใน `dist/YearSetupUpdate/PBudgetManager` ใช้ชุดนี้สร้างแพตช์ ZIP สำหรับอัปเดตจากเมนู **ตั้งค่า → อัปเดตโปรแกรม**

หน้า 9 ช่องบันทึกอัตโนมัติลง SQLite เดียวกับข้อมูลหลัก แถบด้านบนแสดงผลบันทึกจริง หากบันทึกไม่สำเร็จ ให้ลองบันทึกอีกครั้งหรือใช้ Save As เก็บ JSON ก่อนโหลดข้อมูลล่าสุด ระบบป้องกันการเขียนทับเมื่ออีกหน้าต่างแก้ไขข้อมูลก่อน

เมื่อเปิดหน้า 9 ช่องกับฐานข้อมูลที่ยังไม่เคยมีข้อมูลส่วนนี้ ระบบตรวจและย้าย `budget_years_data` จาก localStorage โดยอัตโนมัติ ต้องเปิดด้วยเบราว์เซอร์ โปรไฟล์ และ URL/พอร์ตเดิม สำเนาเดิมในเบราว์เซอร์จะไม่ถูกลบ หากฐานข้อมูลมีข้อมูลแล้วจะไม่ถูกแทนที่อัตโนมัติ สามารถใช้ปุ่มนำเข้าข้อมูลเบราว์เซอร์เดิม หรือเปิด JSON ที่ส่งออกจากโปรแกรมเดิมได้

การเปิด JSON จะตรวจปี โครงการ แหล่งเงินและตัวเลขก่อนแสดงจำนวนปี/รายการให้ยืนยัน ระบบเก็บสำเนาข้อมูลปัจจุบันในฐานข้อมูลและแทนที่ข้อมูลใน transaction เดียวกัน หากผิดพลาดจะยกเลิกทั้งหมด ปุ่ม “สำเนาก่อนนำเข้า” ดาวน์โหลด JSON เก่ามาเปิดเพื่อกู้คืนได้

การดาวน์โหลดฐานข้อมูล SQLite จากเมนูตั้งค่ารวมข้อมูล 9 ช่องและสำเนาก่อนนำเข้าแล้ว ส่วน JSON ส่งออกโครงการจากหน้าหลักยังเป็นข้อมูลโครงการหลักเท่านั้น

ExcelJS 4.3.0 และ FileSaver 2.0.5 อยู่ใน `nine-box-app/vendor` จึงส่งออก Excel ได้โดยไม่ต้องต่ออินเทอร์เน็ต

เมื่อเปิดหน้า 9 ช่อง หน้าหลักจะแสดงสถานะกำลังโหลดจนไฟล์ประกอบและข้อมูลพร้อมใช้งาน หากไม่พบไฟล์ เชื่อมต่อไม่ได้ หรือรอเกิน 35 วินาที จะแสดงข้อความและปุ่ม “ลองใหม่” การเปลี่ยนไปหน้าอื่นยกเลิกการโหลดที่ค้างไว้ ตรวจกรณีผิดพลาดและการลองใหม่ด้วย `python verify_nine_box_loading.py`

สร้าง EXE ลงโฟลเดอร์ใหม่เสมอ เพื่อไม่ให้ขั้นตอน build ลบข้อมูลในชุดที่ใช้งานอยู่:

```powershell
python -m PyInstaller --distpath dist/OfflineUpdate PBudgetManager.spec
python verify_exe.py dist/OfflineUpdate/PBudgetManager/PBudgetManager.exe
python -m unittest -v test_nine_box test_desktop_launcher
python verify_nine_box.py
```

อัปเดตจากในโปรแกรมได้ที่ **ตั้งค่า → อัปเดตโปรแกรม** โดยเลือกไฟล์แพตช์ ZIP ที่ผู้ดูแลจัดทำให้ ระบบปิดโปรแกรมชั่วคราวแล้วเขียนไฟล์ตามรายการใน ZIP ทับในโฟลเดอร์ติดตั้งเดิม โดยไม่เขียนทับฐานข้อมูล `data/master.db` จึงใช้ shortcut เดิมต่อได้

## สำรองอัตโนมัติและอัปเดตโดยรักษาข้อมูลเดิม

หน้าตั้งค่าแสดงพาธฐานข้อมูลที่ใช้งานจริง โฟลเดอร์สำรอง และไฟล์/เวลาสำรองล่าสุด รวมถึงกรณีกำหนด `P_BUDGET_DB` เอง

เมื่อเปิดฐานข้อมูลที่มีอยู่แล้ว ระบบสร้าง SQLite snapshot ล่าสุดทุกครั้งที่เปิดโปรแกรม รวมถึงก่อนอัปเกรดโครงสร้างฐานข้อมูล และตรวจ integrity ก่อนดำเนินการต่อ ถ้าสำรองล้มเหลวจะหยุดเริ่มโปรแกรมเพื่อไม่ปรับฐานข้อมูลโดยไม่มีสำเนา ฐานข้อมูลใหม่จะเริ่มสำรองเมื่อเปิดโปรแกรมครั้งถัดไป การสำรองนี้ทำตอนเปิดโปรแกรม ไม่ใช่งานสำรองตามเวลาขณะที่เปิดค้างไว้

สำเนาอยู่ใน `backups` ข้างฐานข้อมูล โดยเก็บไฟล์ล่าสุดเพียง 1 ไฟล์ ชื่อ `DD_MM_YY_HHMMSS.db` (ปี ค.ศ. 2 หลักและเวลาประเทศไทย) สร้างและตรวจสอบไฟล์ใหม่ก่อนลบสำเนาเก่า ไฟล์ที่ผู้ใช้ดาวน์โหลดไปเก็บที่อื่นไม่ได้ถูกลบตามกติกานี้

ขั้นตอนคือเลือก ZIP เพื่อตรวจสอบรายละเอียด แล้วกด **ติดตั้งแพตช์** โปรแกรมจะปิดเซิร์ฟเวอร์ อัปเดตไฟล์โปรแกรมในโฟลเดอร์เดิม และเปิดโปรแกรมจากตำแหน่งเดิมอีกครั้ง ตัวติดตั้งไม่สร้างสำเนาฐานข้อมูลหรือ rollback ไฟล์โปรแกรม หากอัปเดตถูกขัดจังหวะ ให้ใช้ไฟล์ ZIP เวอร์ชันเดิมติดตั้งซ้ำ ทั้งนี้โปรแกรมยังสร้าง snapshot ฐานข้อมูลอัตโนมัติตอนเริ่มทำงานตามการตั้งค่าปกติ

การอัปเดต ZIP ในโปรแกรมรองรับชุด EXE ที่ใช้ `data/master.db` เท่านั้น

กู้คืนสำเนา: ปิดโปรแกรม เตรียมชุดโปรแกรมที่เข้ากันได้กับฐานข้อมูลพร้อมโฟลเดอร์ data ใหม่ แล้วคัดลอกไฟล์สำรองเป็น `data/master.db` เก็บโฟลเดอร์เดิมไว้ ไม่ผสมไฟล์ WAL/SHM เก่ากับ snapshot และไม่เปิดชุดเดิมกับชุดกู้คืนพร้อมกัน

```powershell
python -m unittest -v test_maintenance test_nine_box test_desktop_launcher
python verify_update.py dist/MaintenanceUpdate/PBudgetManager dist/LoadingUpdate/PBudgetManager
python verify_exe_browser.py dist/YearSetupUpdate/PBudgetManager/PBudgetManager.exe
```

## ทดสอบหน้า 9 ช่องกับ EXE จริง

ใช้ Chrome หรือ Edge ที่ติดตั้งใน Windows พร้อม dependencies จาก `requirements.txt` และติดตั้งเครื่องมือทดสอบแยกจากแอป:

```powershell
python -m pip install --target .browser-check/python -r requirements-test.txt
python verify_exe_browser.py dist/MaintenanceUpdate/PBudgetManager/PBudgetManager.exe
```

ระบุเบราว์เซอร์อื่นด้วย `--browser "C:\path\to\chrome.exe"` ได้ ไม่ต้องดาวน์โหลด browser runtime เพิ่ม Playwright ใช้เฉพาะชุดทดสอบและไม่รวมใน EXE

ชุดทดสอบเปิด EXE จริงบนพอร์ตว่างด้วย SQLite ชั่วคราวและโปรไฟล์เบราว์เซอร์ใหม่ ไม่แตะฐานข้อมูลหรือเซิร์ฟเวอร์ที่ผู้ใช้เปิดอยู่ สร้างโครงการหลักผ่าน API เพื่อเตรียมข้อมูล แล้วใช้การคลิก/พิมพ์ในหน้าเว็บจริงในการเพิ่มเข้า 9 ช่องและแก้ไขตาราง โดยไม่แทนที่ฟังก์ชันบันทึกหรือส่งออกของแอป

ตรวจการบันทึกด้วย Ctrl+S และออกจากช่องกรอก การสลับปีและยอดยกไปปีถัดไป การสลับเมนู การรีโหลด การหยุด EXE และกดลองใหม่หลังเปิด EXE อีกครั้ง รวมถึงเปิดเบราว์เซอร์ใหม่ที่ไม่มี localStorage เพื่อยืนยันข้อมูล SQLite ขณะทดสอบบล็อกคำขอภายนอกของหน้าเว็บและใช้ไลบรารีในเครื่องเท่านั้น ดาวน์โหลด Excel จริงแล้วเปิดด้วย openpyxl เพื่อตรวจชื่อโครงการ ปี และยอดเงินทั้ง 9 ช่องพร้อมผลรวม

ผลทดสอบอยู่ใน `.browser-check/exe-nine-box/<เวลาที่รัน>/`: `report.json`, ภาพหน้าจอ และ `nine-box-export.xlsx` หากไม่ผ่านจะเก็บ traceback และภาพข้อผิดพลาดเมื่อจับภาพได้ พร้อมคืน exit code 1 จึงใช้เป็นเงื่อนไขก่อนส่งมอบ EXE ได้ ควรรันกับชุด EXE ที่จะส่งจริงทุกครั้งหลัง build
